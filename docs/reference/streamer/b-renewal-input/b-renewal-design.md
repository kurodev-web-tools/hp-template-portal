# Streamer B Renewal Design

## Scope
- 対象:
  - `public/templates/streamer/b`
- テンプレート名:
  - `Boss Room`
- この文書は `streamer/b` renewal の詳細設計をまとめる
- カテゴリ全体方針は `STREAMER_RENEWAL_PLAN.md` を参照する

## Renewal Goal
- `streamer` カテゴリ内で、`b` を「ボス戦っぽい見た目のテンプレート」から「支配者と対面する高品質な体験を持つテンプレート」へ格上げする
- 配信者本人の存在感を主役にしつつ、活動情報や参加導線も実サイトとして成立させる
- 既視感のある高級 UI や generic なダッシュボードに落ちず、`BOSS ROOM` として一発で印象に残る renewal を目指す

## Core Experience
- 中心体験:
  - `lock on`
- ユーザーの体感:
  - ページを読むのではなく、支配者と対面しながら視線が絞られていく
- 構造:
  - 疑似固定シーンベース
  - 一定区間は同じ空間に滞在し、スクロールが焦点制御に使われる
- 主役になる印象:
  - ボス部屋の奥にいる配信者へ、部屋全体の空間が収束していく

## Comparison Guardrails
- `a` と被らない点:
  - `a` は潜航と深度、`b` は対面と視線収束
- `r` と被らない点:
  - `r` は潜入や索敵、`b` は支配者との正面対峙
- このテンプレートで避けること:
  - 単なる赤黒の警告 UI
  - tech dashboard 的な細かい情報過多
  - generic なラグジュアリー LP

## World Direction
- 世界観の核:
  - `BOSS ROOM`
- キーワード:
  - 支配
  - 対面
  - 焦点収束
  - 招待制
  - フロア支配
- 色 / 質感:
  - 紫黒ラグジュアリー
- 補助表現:
  - ゲーム的ロックオン UI
  - ターゲットマーカー
  - ステータス表示
- 非採用:
  - 赤黒警告ベース
  - レトロゲーム戦闘画面寄り

## Information Priority
- 1. 支配者の存在
- 2. 支配指標
- 3. 活動内容
- 4. Audience Access Window
- 5. Access Pass / SNS / 参加導線

## Section Structure

### 1. Boss Room Hero
- 役割:
  - 第一印象で「支配者と対面している」空気を成立させる
- 見せるもの:
  - 遠景のキャラクター
  - 部屋全体の圧
  - 焦点収束の兆候
  - Access Pass の存在予告
- スクロール時の変化:
  - 視線が狭まり、遠景から中景へ距離が縮まる

### 2. Character / Ruler Profile
- 役割:
  - どういう支配者なのかを掴ませる
- 見せるもの:
  - 表示名
  - 肩書き
  - 世界観の一文
  - フロアや空間の支配設定
- 方向性:
  - 活動者としての実務情報より先に、支配者としての人格を見せる

### 3. Dominance Metrics
- 役割:
  - どれだけ強い存在かを可視化する
- 見せるもの:
  - 3〜4 個の大型指標
  - 補助的な小ステータス
- ラベル方針:
  - 世界観変換ラベルを使う
- 数値の実体:
  - 登録者数
  - 総視聴規模
  - 平均ライブ反応
  - コミュニティ規模
- 方向性:
  - 細かいダッシュボードではなく、大型指標を主役にする

### 4. Activity / Stream Domain
- 役割:
  - 実際に何を配信しているかを整理する
- 見せるもの:
  - 主配信ジャンル
  - 得意企画
  - 活動スタイル
  - 参加型要素の有無
- 方向性:
  - キャラクター設定を壊さずに、配信者としての実体を見せる

### 5. Audience Access Window
- 役割:
  - 次にこの支配者へアクセスできる時間を提示する
- 見せるもの:
  - 次回配信
  - 今週の access window
  - 公開 / 限定 / 参加条件
- 方向性:
  - 予定表ではなく「入場可能時間」として見せる
  - `a` のログ UI と意味を分ける

### 6. Access Pass / SNS / Participation
- 役割:
  - 参加導線を正式に渡す
- 見せるもの:
  - 視聴導線
  - 通知 / follow
  - X
  - YouTube
  - Discord
  - 必要に応じて membership や限定導線
- 方向性:
  - アイコン列ではなく、招待状 / access pass として見せる

## Character Stage
- キャラクターは空間の中心存在として扱う
- 想定素材:
  - 静止画
  - 背景透過動画
  - 将来のレイヤー分割素材
- 初期印象:
  - 部屋の奥にいる支配者
- 中盤以降:
  - 焦点が合い、中景で存在が確定する

## Character Transition
- 変化軸:
  - `距離`
  - `焦点の明瞭化`
- 基本遷移:
  - `遠景 → 中景`
- 実装前提:
  - 切り替え枚数は少なめにする
  - `a` のような段階的な構図展開にはしない
- 補足:
  - 主役は距離変化そのものより、視線が捕まる感覚

## Motion And Effects
- 主役演出:
  - 空間の圧縮
  - 視線収束
  - ロックオン照準
- 補助演出:
  - UI の焦点化
  - 小さなステータス点灯
  - 余白や暗部の緊張感
- 避けること:
  - グリッチ多用
  - 細かいダッシュボード乱立
  - 部屋より UI の方が目立つ状態

## CTA Strategy
- CTA は配信者側から渡される `Access Pass` として見せる
- 実態は視聴者側の参加導線
- 想定 CTA:
  - `ENTER THE ROOM`
  - `ACCEPT ACCESS`
  - `WATCH LIVE`
  - `REPORT IN`
- 方向性:
  - 命令口調より、選ばれた者だけが入れる招待状の空気感を優先する

## Metrics Direction
- 大型指標 4 本を主役にする
- 例:
  - `Audience Reach`
  - `Total Signal`
  - `Live Response`
  - `Room Members`
- 補助ステータス:
  - `Target Locked`
  - `Room Open`
  - `Signal Stable`
- 基本方針:
  - 数値は現実ベース
  - ラベルだけ世界観へ寄せる
  - リアルタイム取得は必須にしない

## Technical Direction
- 空間収束と照準演出:
  - `three.js / WebGL`
- 疑似固定シーン制御:
  - 通常の JS + CSS
- キャラ切り替え:
  - 画像 / 動画レイヤーの切り替え
- 基本方針:
  - `WebGL` は深度のためではなく、圧縮感、焦点収束、ターゲット認識のために使う
- 非採用:
  - `a` と同型の深海パララックス主役
  - terminal / dashboard 偏重

## Non-Goals
- generic な高級 LP にしない
- tech dashboard に寄せすぎない
- 赤黒の危険区域 UI にしない
- 視聴者主体の「挑戦ボタン」演出を主役にしない

## Why This Direction
- `BOSS ROOM` では、配信者そのものを支配的存在として見せるのが最重要
- `streamer` カテゴリとしては高演出が求められるが、`a` と同じ方向へは行かない方が強い
- 疑似固定シーンと視線収束を使うことで、「読む」より「対面する」体験を作れる
- 高品質 renewal として、最初から `WebGL` を前提にした設計で進める

## Implementation Notes
- 固定しすぎて読めないページにしない
- 疑似固定シーン内でも活動情報と schedule は読み取れる密度に保つ
- Access Pass 導線は最後に集約し、途中では存在だけを匂わせる
- キャラクターが空間の中心にいないとテーマが崩れるので、レイアウトで最優先する
- 顧客案件では、表示名や world one-liner を先に決めないと見出しがテンプレート臭くなりやすい

## Open Knobs
- キャラ素材が静止画か透過動画か
- 大型指標 4 本の具体ラベル
- Access Pass の文体をどこまで高圧にするか
- audience access window の公開 / 限定ラベル粒度

## Readiness Check
- renewal の狙いが明確
- `a` / `r` との差別化が明確
- 中心体験が明確
- 支配指標の扱いが明確
- CTA と schedule の扱いが明確
- 技術方針が明確
- 非採用案が明確

現時点で、別セッションで `streamer/b` renewal 用 worktree を切って実装へ入れる粒度としては十分。
