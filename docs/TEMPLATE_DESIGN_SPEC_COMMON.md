# ストリーマー Next.js 詳細設計 共通基盤

## 目的

- この文書は、`streamer` の新規テーマ A-Z を React + Next.js で実装するときの共通基盤を定義する
- 既存の静的 HTML テンプレート群は対象外とし、新規テーマ側の設計判断だけを固定する
- 各テーマの詳細設計は、この文書を前提にして同じ粒度で書く

---

## 1. 固定する技術スタック

### 1.1 コア

| 技術 | 役割 |
|------|------|
| Next.js | App Router のルーティング、静的出力、ページ構成 |
| React | UI 構築の基盤 |
| TypeScript | 型安全なデータモデルとテーマ設定 |
| Node.js | ローカル実行、ビルド、検証 |

### 1.2 スタイリング

| 技術 | 役割 |
|------|------|
| Tailwind CSS | レイアウト、余白、レスポンシブ制御 |
| CSS Variables | テーマ色、背景、影、角丸の共通トークン |
| shadcn/ui | 必要時のみ使う基本 UI。基盤依存にはしない |

### 1.3 アニメーション

| 技術 | 役割 |
|------|------|
| GSAP | スクロール連動、出現、タイミング制御 |
| React Three Fiber | テーマの核が 3D である場合のみ使用 |
| Framer Motion | 基盤必須にはしない。必要なテーマのみ個別採用 |

### 1.4 表示資産

| 技術 | 役割 |
|------|------|
| next/font | フォント配信 |
| Lucide React | アイコン |
| next/image | 画像最適化。export 方針に合わせて設定する |

### 1.5 レンダリング方針

- 基本方針は static-first
- サーバー依存の状態管理、DB 接続、認証セッション前提にはしない
- 1 テーマ = 1 つの主ページを基本にする
- 追加ページは、そのテーマの表現上どうしても必要なときだけ増やす
- 3D は常時表示の前提にしない。まず静的レイアウトが成立することを優先する

### 1.6 推奨ディレクトリ

```text
app/
  streamer/
    [code]/
      layout.tsx
      page.tsx
      metadata.ts
components/
  streamer/
    shared/
    themes/
lib/
  streamer/
    theme-definitions.ts
    streamer-profile.ts
```

## 2. 共通ページ骨格

新規テーマは、以下の 5 つを標準骨格として持つ。

### 2.0 レイアウトモード

まず、各テーマは次のいずれかのレイアウトモードを選ぶ。

- `LP single page`
  - 1 ページ完結
  - もっとも標準的な形式
  - 情報の大半を縦スクロールで見せる
- `LP + subpages`
  - トップページは LP 風
  - 必要な補助ページだけ下層に分ける
  - 例: about / schedule / gallery / contact
- `subpage-centered`
  - 下層ページのほうが主役
  - 情報量が多い、または体験の切り替えが重要なテーマ向け

標準は `LP single page`。  
下層ページを増やす場合は、そのページが Hero の補足ではなく、独立した役割を持つことを説明する。

### 2.1 ヘッダー位置

ヘッダーは次のいずれかで定義する。

- `top fixed`
  - 最も標準的
  - LP、一般的な紹介ページ、情報整理型に向く
- `side panel`
  - 左右のどちらかに固定パネルを置く
  - cockpit / HUD / world-navigation 系のテーマ向け
- `floating overlay`
  - 余白の上に浮かぶ軽いナビゲーション
  - 演出優先だが、操作性は崩さない

PC ではヘッダー位置をテーマの主役体験に合わせる。  
SP では原則として `top fixed` か折りたたみメニューに寄せる。

### 2.2 ナビゲーション形式

ナビゲーションは次のいずれかを選ぶ。

- `top nav`
  - 標準的なリンク列
- `side dots`
  - 縦方向のセクションナビ
  - ショート LP と相性が良い
- `section cards`
  - セクションをカードとして選ばせる
  - 企画系、ゲーム的導線向け
- `world-in-UI`
  - 世界観の UI の一部としてナビゲーションを見せる
  - HUD、端末、魔導書、コクピットなどに向く

ナビゲーションは見た目の演出より、現在位置の分かりやすさを優先する。

### 2.3 下層ページ追加基準

下層ページを追加してよいのは、次のいずれかに当てはまるとき。

- 情報量が多く、LP 1 枚では読みにくい
- 時間や状態で見せ方が変わる
- アーカイブ、実績、ギャラリーなど独立した閲覧価値がある
- 世界観上、移動や分岐そのものが意味を持つ

逆に、Hero の補足程度なら下層ページに分けない。  
ページが増えるほど保守コストが増えるため、最小限に留める。

### 2.4 PC / SP の役割差

- PC
  - 世界観、演出、視線誘導を優先する
  - サイドパネル、複数カラム、視差表現を使いやすい
- SP
  - 可読性、操作性、CTA 到達性を優先する
  - 1 カラム化、ナビ圧縮、演出削減を基本とする

SP では「PC の縮小版」ではなく、情報の優先順位を組み替えた見せ方にする。

### 2.5 セクション数の標準上限

- LP single page: 5〜6 セクションを標準
- LP + subpages: トップは 4〜5 セクション、補助ページは各 1 目的
- subpage-centered: 必要最小限のトップ + 下層ページを中心

6 セクションを超える場合は、テーマ側の設計書で「なぜ分けるか」を書く。

### 2.6 Hero

- テーマの世界観を最初の 1 画面で伝える
- 表示名、肩書き、短いコンセプト、主要 CTA を置く
- 3D を使う場合でも、文字情報だけで意味が分かる構成を保つ

### 2.7 Profile

- 配信者の実像を説明する
- 何を配信しているか、どんな人格で見せるか、どこへ誘導するかを明確にする
- 世界観コピーよりも、活動内容の分かりやすさを優先する

### 2.8 Content

- 代表配信、企画、作品、実績、アーカイブ、世界観要素のいずれかを見せる
- テーマごとに名称は変えてよいが、役割は「活動の中身を見せる」で固定する

### 2.9 Schedule

- 次回配信、固定枠、定例イベント、公開予定などの時間情報を見せる
- 状態表示を持たせる場合は offline / live / upcoming を共通語彙として扱う

### 2.10 Contact / CTA

- 配信視聴、通知登録、SNS、依頼、参加導線のいずれかに誘導する
- CTA の文言は世界観に合わせてよいが、目的は常に行動に寄せる

### 2.11 Footer

- SNS、コピーライト、補助リンク、簡単な戻り導線を置く

### 2.12 可変範囲

- セクション名はテーマごとに変えてよい
- 順番は Hero -> Profile -> Content -> Schedule -> Contact を原則とする
- ただし、テーマの核が「回遊」「探索」「ステージ」など別体験なら、Hero の直後に主役セクションを挿入してよい
- 追加セクションは 2 つまでを標準とし、それ以上は複雑化の理由を設計書に書く

## 3. 共通データモデル

### 3.1 必須フィールド

```ts
type StreamerThemeData = {
  themeCode: string
  themeName: string
  streamerName: string
  roleTitle: string
  tagline: string
  introShort: string
  introLong: string
  primaryCTA: {
    label: string
    href: string
  }
  profile: {
    genre: string
    mainPlatform: string
    language: string
    since: string
  }
  socials: {
    youtube?: string
    twitch?: string
    x?: string
    tiktok?: string
    discord?: string
    booth?: string
  }
  schedule: {
    summary: string
    nextStream?: string
    weekly?: Array<{
      day: string
      time: string
      content: string
    }>
  }
}
```

### 3.2 任意フィールド

- `secondaryCTA`
- `featuredContents`
- `stats`
- `gallery`
- `achievements`
- `supportSettings`
- `themeSpecific`

### 3.3 拡張ルール

- 共通 UI は必須フィールドだけで描画できるようにする
- テーマ固有の情報は `themeSpecific` に閉じ込める
- 追加フィールドは自由に増やしてよいが、共通コンポーネントはそれに依存しない
- `themeSpecific` はテーマの見た目や演出に必要なものだけを持たせる

### 3.4 失敗時の扱い

- 画像がなくても成立する
- スケジュールが未設定でも Hero / Profile / Contact は表示する
- SNS が空でも CTA は 1 つ以上表示する

## 4. デザイントークン

### 4.1 1 テーマ 1 トークンセット

各テーマは次のトークンを必ず定義する。

- `color.primary`
- `color.secondary`
- `color.accent`
- `color.background`
- `color.surface`
- `color.text`
- `color.muted`
- `shadow.soft`
- `shadow.strong`
- `radius.md`
- `radius.lg`
- `font.display`
- `font.body`

### 4.2 ルール

- 色は CSS Variables を正本にする
- Tailwind のユーティリティはトークンを読むだけにする
- 1 テーマ内で直接 hex を散らさない
- テーマ間で似た色でも、背景・明度・コントラストの扱いで差を作る

### 4.3 比較基準

- 明度差で可読性を確保する
- アクセント色は 1 つを主役にする
- 背景が強いテーマは、文字面の密度を抑える

## 5. 動きと 3D のルール

### 5.1 デフォルト

- まず静止状態で完成させる
- GSAP は出現、スクロール、視線誘導に使う
- ホバーやタップは軽く返す

### 5.2 3D を使う条件

R3F を標準採用するのは、次のどれかを満たすテーマだけ。

- 世界観の核が「空間」や「物体の存在感」にある
- Hero の主役が 3D オブジェクトでないと意味が薄い
- 2D では置き換えられない表現効果が必要

### 5.3 3D の制約

- 3D は Hero か 1 セクションに限定する
- 常時アニメーションは最小限にする
- モバイルでは粒子数、ポストエフェクト、影を落とす
- オート回転や追従カメラは、テーマ上の意味がある場合だけ使う

### 5.4 reduced motion

- `prefers-reduced-motion` では連続アニメーションを止める
- 代替として、静止レイアウトと明確な CTA を残す
- 3D がある場合でも、静止したヒーロービジュアルに落とす

### 5.5 フォールバック

- 3D が読み込めない場合は CSS / 画像 / SVG で代替する
- 動きがなくてもテーマの印象が崩れない構成にする

## 6. レスポンシブとアクセシビリティ

### 6.1 レスポンシブ基準

- PC を基準にデザインを決める
- SP は 1 カラム化、余白調整、主要 CTA の前倒しを優先する
- モバイルでは視覚効果よりも可読性と操作性を優先する

### 6.2 アクセシビリティ

- すべての画像に代替テキストを持たせる
- コントラスト比を落としすぎない
- キーボード操作で CTA に到達できるようにする
- 装飾要素はスクリーンリーダーの邪魔にしない

---

## 7. 検証ルール

### 7.1 基本チェック

- リンク切れがない
- metadata が埋まっている
- placeholder が公開文言に残っていない
- PC / SP で大きく崩れていない
- CTA が実在の導線として理解できる

### 7.2 共通コマンド

- HTML / link 変更時: `npm run audit:links`
- metadata / placeholder 変更時: `npm run audit:metadata`
- テーマ個別の品質確認: 該当テストを追加して実行する

### 7.3 受け入れ条件

- 1 ページ目でテーマの差が分かる
- 文章だけで活動内容が分かる
- 3D がなくても成立する
- モバイルで CTA が埋もれない
- 共通コンポーネントだけで最低限の体裁が保てる

## 9. まとめ

- 共通化するのは「土台」
- 差別化するのは「世界観」と「主役の体験」
- 迷ったら、共通 UI は静かに、テーマ固有の部分だけを強くする
